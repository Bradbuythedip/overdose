# The rich-list oracle is 39% junk -- and why that does not change the nulls

Measured while chasing a vanity-address lead, not assumed.

## What was found

`harness.Oracle.addrs` -- the in-memory first-pass oracle, 1,720,292 entries --
was sampled at 20,000 entries and checked for base58 validity:

```
parseable as a mainnet address   12,229   61.1%
unparseable                       7,771   38.9%
```

Examples of the unparseable entries:

```
3cf8c658a4b62c68197eb334b339d538c74     <- a hex scripthash, not an address
1ToXicAGwzH37HRAYAes6Jww2NKUo6qBgt      <- decodes to 26 bytes, not 25
1NoNQJhtHTncTvZUya5rKK9sZVSgE7giqd      <- checksum fails
```

So the rich list mixes real addresses with hex scripthashes and corrupted
strings. Its effective size is nearer 1.05M real addresses than 1.72M.

## Why the sweeps are unaffected

The rich list is only a fast pre-filter. Two properties save it:

1. **It cannot produce false positives.** `funded()` is a string set-membership
   test, and every address we test is generated by our own derivation, so it is
   always well-formed. A junk entry simply never matches anything.
2. **It is not the authoritative oracle.** `address_map.bin` is, and it is keyed
   by `sha256(scriptPubKey)` built from our own derived addresses, so the rich
   list's contents cannot reach it at all. That index was separately calibrated
   at **13,410/13,410** known-funded addresses across all four script types
   (`window/oracle_calibrated.md`).

The one real cost is that the rich list contributes less coverage than its
entry count suggests. Since every sweep also queries the full index, nothing
was missed.

## The vanity lead this came from, closed

Scanning the 1.72M rich-list strings for puzzle-relevant vanity patterns
(overdose, keiser, toxic, salvador, bukele, volcano, maximalist, layer1, ...)
returned 20 matches, the striking one being `1ToXicAGwzH37HRAYAes6Jww2NKUo6qBgt`
against the column's own headline BITCOIN IS TOXIC AF.

It is **not a Bitcoin address**: it base58-decodes to 26 bytes and fails its
checksum. Neither does `3Wyj2haTBp8kafu7D9XKPL12d6ToXicHmJ`. Both are junk
entries of exactly the kind measured above. The vanity-address hypothesis is
closed for this data set.
